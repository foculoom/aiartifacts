# Product-testing persona evaluations

These are original synthetic inputs for the existing experience-review skill,
not transcripts of real customers. Give a fresh evaluator the candidate skill,
its product-testing reference and **only** [inputs.md](inputs.md). Retain its
complete answer before opening [assessment.md](assessment.md). Record exact
input and skill hashes, reviewer type, tools and limitations. Do not turn a
source-guidance or text-case pass into rendered or human acceptance.

Cases cover relevant selection for apps and games, evidence limits, no-UI scope,
accessibility overlays, unauthorized side effects and harness false positives.
There is no requirement to run every lens for every product. Each owning project
retains its own acceptance policy and any required human study.

For a candidate guidance change, first verify local links and unchanged catalog
discovery, then evaluate these decisions independently. Before a claim that the
guidance improves actual testing, exercise representative app and game journeys
on named rendered artifacts and preserve complete results under the existing
[production-acceptance method](../../../plugins/design/skills/experience-review/references/production-acceptance.md).
If claiming incremental usefulness, use a predeclared matched comparison; do not
select favorable reruns. Existing rendered fixtures can supply those artifacts.
Publication and consumer adoption require their separate reviewed workflow.
