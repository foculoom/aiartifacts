This includes:\nL24: \nL25: - Programming languages and frameworks\nL26: - Development methodologies and best practices\nL27: - Architecture patterns and design principles\nL28: - Testing strategies and quality assurance\nL29: - DevOps and deployment practices\nL30: - Accessibility and inclusive design\nL31: - Performance optimization techniques\nL32: If you are planning to contribute content that involves paid services, please review our [Guidance for submissions involving paid services](https://github.com/github/awesome-copilot/discussions/968).\nL33: ## What We Don't Accept\nL34: \nL35: To maintain a safe, responsible, and high-signal collection, we will **not accept** contributions that:\nL36: - **Violate Responsible AI Principles**: Content that attempts to circumvent Microsoft/GitHub's Responsible AI guidelines or promotes harmful AI usage\nL37: - **Compromise Security**: Instructions designed to bypass security policies, exploit vulnerabilities, or weaken system security\nL38: - **Enable Malicious Activities**: Content intended to harm other systems, users, or organizations\nL39: - **Exploit Weaknesses**: Instructions that take advantage of vulnerabilities in other platforms or services\nL40: - **Promote Harmful Content**: Guidance that could lead to the creation of harmful, discriminatory, or inappropriate content\nL41: - **Circumvent Platform Policies**: Attempts to work around GitHub, Microsoft, or other platform terms of service\nL42: - **Duplicate Existing Model Strengths Without Meaningful Uplift**: Submissions that mainly tell Copilot to do work frontier models already handle well (for example, generic TypeScript, HTML, or other broadly-supported coding tasks) without addressing a clear gap, specialized workflow, or domain-specific constraint. These contributions are often lower value for users and can introduce weaker or conflicting guidance than the model's default behavior.\nL43: - **Unreviewed remote-source plugins**: Do not open a pull request that directly adds a third-party plugin to `plugins/external.json`. Skills use the standard `skills/` directory; Copilot-specific content uses `com.github.copilot/`.\nL176: - **Valid references**: All paths referenced in plugin.json must point to existing source files in the repository\nL177: - **Reusable extensions**: Curated plugins can bundle extensions by adding `./extensions/<name>` paths under `extensions.com.github.awesome-copilot.extensions`; the same extension can be listed by multiple plugins\nL178: - **Instructions excluded**: Instructions are standalone resources and are not part of plugins\nL179: - **Clear purpose**: The plugin should solve a specific problem or workflow\nL180: - **Validate before submitting**: Run `npm run plugin:validate` to ensure your plugin is valid\nL181: #### Adding External Plugins\nL182: \nL183: External plugins are plugins hosted outside this repository and listed in `plugins/external.json`. Public contributors should **not** open a PR that edits `plugins/external.json` directly. Instead, submit external plugins through the public review workflow below.\nL184: \nL185: > [!IMPORTANT]\nL186: > Public external plugin submissions are GitHub-only in v1. The submitted plugin must live in a public GitHub repository and use `source.source: \"github\"`.\nL187: ##### Submission fields\nL188: \nL189: The external plugin issue form will collect these fields:\nL190: - Plugin name\nL191: - Short description\nL192: - GitHub repository in `owner/repo` format\nL193: - Plugin path inside the repository (optional when the plugin is at the repository root)\nL194: - Ref to review (`ref`), using a release tag or tag ref rather than a branch\nL195: - Commit SHA to review (`sha`), using a full 40-character commit SHA\nL196: - Plugin version\nL197: - License identifier\nL198: - Author name\nL199: - Author URL (optional)\nL200: - Homepage URL (optional)\nL201: - Keywords/tags\nL202: - Additional notes for reviewers (optional)\nL203: - Confirmation checkboxes that the repository is public, the submitted ref and/or sha is immutable, the submission follows this repository's policies, and the plugin is not a duplicate listing\nL204: The repository's canonical validation rules live in `eng/external-plugin-validation.mjs`. Build scripts reuse the `marketplace` policy from that module, and the issue intake automation uses the stricter `publicSubmission` policy so the JSON contract and workflow checks stay aligned.\nL205: \nL206: For entries committed to `plugins/external.json`, the current marketplace validation requires:\nL207: - `name`, `description`, and `version` (a valid [semantic version](https://semver.org), e.g. `1.2.3`)\nL208: - `author.name` (and, when present, a valid `author.url` and `author.email`)\nL209: - `repository` as an HTTPS GitHub URL\nL210: - `keywords` as lowercase hyphenated tags\nL211: - `license`, when provided, is recommended to be an [SPDX identifier or expression](https://spdx.org/licenses) (e.g. `MIT`, `Apache-2.0`, `MIT OR Apache-2.0`), but a non-SPDX or proprietary license is allowed and only produces a warning\nL212: - `source.source: \"github\"` plus `source.repo` in `owner/repo` format\nL213: - optional `source.path` values of `/` for repository root, or a repository-relative folder where the plugin structure starts (do not point to `plugin.json` directly)\nL214: Validation also emits non-fatal warnings to catch mistakes early: unknown/misspelled top-level, `author`, or `source` fields; `license` values that are not recognized SPDX identifiers (non-SPDX/proprietary licenses are permitted, not rejected); and marketplace entries whose `source` omits an immutable `ref`/`sha` locator. The same `license` validation is shared with local plugin `plugin.json` manifests so both are checked consistently.\nL215: The public-submission policy builds on those rules and also requires `license` plus at least one immutable source locator: `source.ref`, `source.sha`, or both.\nL216: ##### Review workflow\nL217: 1. **Open an issue** using the external plugin issue form. Automation applies the `external-plugin` and `awaiting-review` labels.\nL218: 2. **Automated intake validation** checks that the required fields are present and correctly formatted for a GitHub-hosted plugin. Invalid submissions are labeled `requires-submitter-fixes` with a comment explaining what must be fixed before maintainer review.\nL219:    Intake also checks the repository owner's type using the GitHub API. Organization-owned repositories receive `first party` for the `Microsoft`, `GitHub`, `Azure`, `dotnet`, `MicrosoftDocs`, or `microsoftgraph` organizations (case-insensitive), or `third party` for any other organization. User-owned repositories receive neither label. On the triage board, `first party` skips AI review and creates an `Accept` recommendation with `/approve`; this is only a triage recommendation.\nL220: Submissions must still pass automated validation and quality gates, and a human maintainer must review and approve them before listing. Ownership labels are updated on each intake pass.\nL221: 3. **Automated quality gates** run after metadata validation:\nL222:    - Agent Plugins v1.0.0 manifest compliance, including a root `plugin.json` with the required schema and supported fields\nL223:    - `vally lint` against the submitted plugin path/ref/sha, including Agent Skills spec compliance and valid file references for bundled skills\nL224:    - install smoke test via Copilot CLI against an ephemeral marketplace entry generated from the submission\nL225:    - version matching against the source manifest, ref/SHA consistency when both locators are provided, and the required extension structure for plugins tagged `canvas`\nL226:    All applicable quality gates must pass. Spec compliance violations and lint failures are blocking errors, not warnings. Infrastructure errors keep the submission in `awaiting-review` until checks can complete or a maintainer explicitly overrides the blocker.\nL227: 4. **Ready for maintainer review**: if metadata validation and quality gates pass, automation removes `awaiting-review` and adds `ready-for-review`.\nL228: 5. **Submitter-fix blocker**: if metadata is valid but quality gates fail, automation applies `requires-submitter-fixes` instead of advancing to human review.\nL229: 6. **Requesting another intake pass**: after updating the issue body or source plugin, the issue author or a maintainer can comment `/rerun-intake` to re-run automated intake and quality gates on demand while the issue is still open. Open issues re-trigger intake automatically on edit. When the rerun is accepted, automation reacts to the command comment with 👀 so it is visible that processing started.\nL230: 7. **Maintainer override path**: a maintainer with write access can comment `/mark-ready-for-review [optional reason]` to explicitly move a `requires-submitter-fixes` issue to `ready-for-review`. Conversely, `/request-fixes <reason>` moves an open, undecided submission to `requires-submitter-fixes` and records the requested fixes in an issue comment; the submitter's edit or `/rerun-intake` re-enters intake.\nL231: 8. **Maintainer decision**: once in `ready-for-review`, a maintainer with write access performs the manual review, then comments `/approve` or `/reject <reason>` on the issue. Commands from non-maintainers are ignored.\nL232: 9. **Approval path**: on `/approve`, automation removes `ready-for-review`, adds `approved`, closes the issue, and opens or updates a PR against `main` that updates `plugins/external.json` and generated marketplace outputs.\nL233: 10. **Rejection path**: on `/reject <reason>`, automation removes `ready-for-review`, adds `rejected`, closes the issue, and records the reason in an issue comment. Rejected issues are terminal: `/rerun-intake` no longer reopens them, so a submitter who believes the concerns are fully addressed must open a new external plugin submission issue.\nL234: ##### Updating listed external plugins via PR\nL235: \nL236: When a pull request updates `plugins/external.json` (for example, version updates for a previously approved listing), automation runs PR quality checks and posts the result directly on the PR:\nL237: 1. **Detect changed entries**: automation identifies added/updated external plugin entries in the PR.\nL238: 2. **Run quality gates**: automation runs the same blocking quality gates as submission intake against each changed plugin source ref/SHA/path, including manifest compliance, Agent Skills spec compliance via `vally lint`, and install smoke tests.\nL239: 3. **Post source links**: automation updates a bot comment with per-plugin results and direct GitHub tree links to each plugin source location.\nL240: 4. **Sync workflow-state labels on the PR**:\nL241:    - `ready-for-review` when all checks pass\nL242:    - `requires-submitter-fixes` when quality checks fail due to plugin issues\nL243:    - `awaiting-review` when checks cannot complete because of infrastructure/transient errors\nL244: 5. **Fail the PR status check**: the `enforce-quality-gates` job fails unless every changed plugin passes every applicable gate, so the PR shows a failing check (blocking merge when configured as a required status check) while any gate is failing or incomplete.\nL245: ##### Website README\nL246: \nL247: External plugin detail pages load their README from GitHub during website data\nL248: generation.
